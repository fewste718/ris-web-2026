# API-контракт

## Таблица API

| Метод и путь | Тело запроса | Успех | Ошибки |
|---|---|---|---|
| POST /api/auth/login | login, password | 200, id, login, fullName, role вошедшего пользователя | 400, 401 |
| GET /api/equipment | — | 200, массив: id, name, clientId, clientName | 401, 403 |
| GET /api/users?role=Engineer | — | 200, массив: id, fullName инженеров | 401, 403 |
| GET /api/support-tickets | — | 200, массив заявок или `[]` | 400, 401 |
| GET /api/support-tickets/{id} | — | 200, заявка | 401, 403, 404 |
| POST /api/support-tickets | title, equipmentId, description | 201, созданная заявка; Location с адресом записи | 400, 401, 403 |
| PATCH /api/support-tickets/{id}/assignee | assigneeUserId | 200, обновлённая заявка | 400, 401, 403, 404, 409 |
| PATCH /api/support-tickets/{id}/status | status | 200, обновлённая заявка | 400, 401, 403, 404, 409 |

Для списка допустим фильтр `GET /api/support-tickets?status=New`. Если параметр не передан, возвращаются все доступные пользователю статусы. Неизвестный код фильтра — `400`; пустой результат — `200` и `[]`.

## Доступ и правила

- Диспетчер получает общий список и любую заявку. Инженер получает только заявки, где `assigneeUserId` совпадает с его идентификатором. Фильтр не расширяет доступ; прямой запрос чужой заявки инженером возвращает `403`.
- Список оборудования и список инженеров доступны диспетчеру для заполнения формы и назначения. Управление справочниками через API не предусмотрено.
- При создании клиент приложения передаёт только `title`, `equipmentId`, `description`. Сервер задаёт `id`, `number`, `createdAt`, автора из контекста входа, `New` и пустого исполнителя.
- После удаления пробелов по краям длина `title` — 5–80 символов, `description` — 10–500. `equipmentId` — положительное целое число со ссылкой на существующее оборудование и клиента. Неверные данные — `400`, запись не создаётся.
- Назначение и смена статуса — отдельные PATCH. Меняются только поля соответствующего действия; остальные данные заявки сохраняются.
- Назначает или переназначает только диспетчер и только при `New`. `assigneeUserId` — положительный целочисленный идентификатор существующего пользователя с ролью `Engineer`; неверное значение — `400`.
- Переходы `New → InProgress` и `InProgress → Closed` выполняет только назначенный инженер. Диспетчер может выполнить `New → Cancelled` и `InProgress → Cancelled`.
- Другие переходы, изменение `Closed` или `Cancelled` и назначение после начала работы отклоняются. Отмена сохраняет запись и исполнителя; удаление заявки не предусмотрено.
- Поля `equipmentName`, `clientId`, `clientName`, `assigneeFullName` в ответе формируются по связанным сущностям и не дублируются в таблице заявок. `passwordHash` никогда не возвращается.

## Коды ошибок

| Код | Смысл |
|---|---|
| 400 | Некорректные поля, неизвестный код статуса или недопустимая ссылка в теле запроса |
| 401 | Нет действительного входа либо неверный логин или пароль |
| 403 | Пользователь вошёл, но не имеет права на действие или заявку |
| 404 | Заявка с указанным id не существует |
| 409 | Действие разрешено роли, но недопустимо в текущем состоянии заявки |

Например, неизвестный код `Done` возвращает `400`; попытка назначенного инженера выполнить `New → Closed` — `409`; попытка другого инженера менять заявку — `403`. При ошибке изменения не сохраняются, возвращается понятное сообщение.

## Пример создания заявки

`POST /api/support-tickets`

```json
{
  "title": "Не печатает сетевой принтер",
  "equipmentId": 7,
  "description": "После отправки задания документ не появляется в очереди принтера"
}
```

Ответ: `201 Created`, `Location: /api/support-tickets/17`.

```json
{
  "id": 17,
  "number": "SUP-2026-0001",
  "title": "Не печатает сетевой принтер",
  "equipmentId": 7,
  "equipmentName": "Сетевой принтер 01",
  "clientId": 3,
  "clientName": "Клиент А",
  "description": "После отправки задания документ не появляется в очереди принтера",
  "status": "New",
  "createdByUserId": 1,
  "assigneeUserId": null,
  "assigneeFullName": null,
  "createdAt": "2026-10-17T12:00:00Z"
}
```

`clientId = 3` определяется по записи оборудования 7. `createdByUserId = 1` — вошедший диспетчер. Клиент и автор заявки не совпадают по смыслу. Технический `id = 17` используется в URL, а `number` сообщают клиенту.

## Пример назначения инженера

Диспетчер выполняет `PATCH /api/support-tickets/17/assignee`.

```json
{
  "assigneeUserId": 2
}
```

Ответ: `200`, заявка с `assigneeUserId = 2`, именем выбранного инженера и прежним статусом `New`.

## Пример смены статуса

Назначенный инженер 2 выполняет `PATCH /api/support-tickets/17/status`.

```json
{
  "status": "InProgress"
}
```

Ответ: `200`, заявка со статусом `InProgress` и прежним исполнителем. Для закрытия он передаёт `Closed`; для отмены диспетчер передаёт `Cancelled` тем же отдельным запросом статуса.
