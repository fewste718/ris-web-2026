## Запуск клиента

Требуется Node.js 24 LTS версии 24.12 или новее.

```bash
cd frontend
npm install
cp .env.example .env
npm run dev
```

Открыть адрес из терминала, обычно http://localhost:5173.

В приложении три экрана: список заявок, создание заявки и вход. Список и форма обращаются к API-модулю. При `npm run dev` учебный HTTP mock отвечает на `/__mock/api/support-tickets`; данные находятся в памяти dev-сервера и сбрасываются при его перезапуске. Обновление вкладки повторно загружает этот список. Форма входа демонстрационная, авторизация не выполняется.

В `.env` задаётся `VITE_API_BASE_URL=http://localhost:5000`. Этот файл исключён из Git, в репозитории хранится `.env.example`. После изменения переменной нужно перезапустить Vite. Выбор mock или реального `fetch` находится только в `src/api/tickets.js`. В сборке без dev-сервера используется прямой JavaScript mock; его данные сбрасываются при обновлении вкладки.

Для проверки в режиме разработки:

| Адрес | Проверка |
|-------|----------|
| `/` | Загрузка и список заявок |
| `/?mock=empty` | Пустой список |
| `/?mock=500` | Ошибка загрузки |
| `/new?mock=500` | Отказ создания с HTTP 500 |
| `/new?api=real` | Реальный запрос к порту 5000; при выключенном API — отсутствие связи |
| `/dev/api-check.html` | Вызов API напрямую: успешное создание и HTTP 400 для темы `abc` |

Учебные параметры учитываются API-модулем при загрузке страницы только в режиме разработки. Для возврата к обычному режиму откройте `/` без параметров с обновлением страницы. На проверочной странице откройте F12 → Network → Fetch/XHR, затем нажмите «Создать корректную заявку» и «Отправить тему abc»: появятся POST со статусами `201` и `400`. Обработчик mock подключён только к dev-серверу; учебная страница не включается в production-сборку.

Проверка сборки из папки `frontend`:

```bash
npm run build
```

## Запуск backend

Требуется .NET SDK 9.0. Проект использует `net9.0`.

Из корня репозитория:

```bash
cd backend
dotnet restore
dotnet run
```

Профиль `http` из `backend/Properties/launchSettings.json` задаёт среду `Development` и порт `5000`.

| Адрес | Назначение |
|-------|------------|
| `http://localhost:5000` | Базовый адрес API |
| `http://localhost:5000/swagger/index.html` | Интерактивный Swagger в Development; `/swagger` перенаправляет сюда |
| `http://localhost:5000/health` | Проверка живости процесса: HTTP 200 и `ok` |
| `http://localhost:5000/info` | Название приложения, среда, версия и номер лабораторной |

`/health` проверяет только живость процесса, а не создание заявки. Он не принимает поля заявки и не подтверждает работу POST. Создание и чтение заявок проверяются отдельными запросами API ЛР8.

Данные заявок пока в памяти, после перезапуска backend пропадут. При запуске сервера список заявок пуст. Vue продолжает работать с mock отдельно от backend. PostgreSQL на этом этапе не подключён.

`InfoController` получает `IApplicationInfoService` через конструктор; реализация зарегистрирована в DI в `Program.cs`. Сборочные папки `backend/bin` и `backend/obj` исключены из Git. Для остановки сервера нажмите Ctrl+C.

## API заявок

Главная сущность — `SupportTicket`, ресурс — `/api/support-tickets`. В теле создания передаются только `title`, числовой `equipmentId`, `description`. После удаления пробелов по краям длина темы — 5–80 символов, описания — 10–500. Сервер задаёт `id`, отдельный номер вида `SUP-2026-0001`, `New`, автора и время создания; исполнителя при создании нет. Организация-клиент определяется через оборудование.

| Метод и путь | Успех |
|--------------|-------|
| `POST /api/support-tickets` | 201, созданная заявка и Location |
| `GET /api/support-tickets` | 200, список или `[]` |
| `GET /api/support-tickets/{id}` | 200, одна заявка |
| `PATCH /api/support-tickets/{id}/assignee` | 200, исполнитель изменён, статус сохранён |
| `PATCH /api/support-tickets/{id}/status` | 200, статус изменён отдельным действием |

Для списка доступен фильтр `?status=New` или другой из четырёх статусов. Инженер получает только назначенные ему заявки, фильтр не расширяет этот список.

В ЛР8 каждый запрос к `/api/support-tickets` должен содержать заголовок `X-User-Id` с положительным числовым ID сотрудника. Это учебный способ указать действующего пользователя; настоящий вход появится в ЛР11. Служебным `/health` и `/info` этот заголовок не нужен.

| X-User-Id | Сотрудник | Действия |
|-----------|-----------|----------|
| 1 | Диспетчер 1 | Создать, назначить инженера при New, отменить New или InProgress |
| 2 | Инженер 1 | Читать свои заявки, переводить свою New в InProgress, затем в Closed |
| 3 | Инженер 2 | Те же действия только со своими заявками |

Оборудование: `7` — «Сетевой принтер 01», клиент `3` («Клиент А»); `8` — «Файловый сервер 01», клиент `4` («Клиент Б»). Допустимые исполнители — сотрудники `2` и `3`.

Назначение принимает `{ "assigneeUserId": 2 }`, смена статуса — `{ "status": "InProgress" }`. Назначение не переводит заявку в работу. Без исполнителя взять в работу нельзя. После начала работы переназначение запрещено, Closed и Cancelled неизменяемы. Отмена сохраняет запись и назначенного исполнителя. DELETE и общий PATCH отсутствуют.

Некорректный JSON, поля, справочные ссылки и неизвестные статусы возвращают 400; отсутствующая заявка — 404; запрещённое действие — 409. По правилам ЛР8 чужие действия тоже возвращают 409, до введения настоящей авторизации и 403 в ЛР11. Неожиданный сбой возвращает безопасный ProblemDetails с кодом 500; сервер пишет операцию, ID и тип ошибки без полного тела запроса. Искусственный сбой, использованный для проверки лога, удалён.

В Postman выберите Import и откройте `docs/api-collection/support-tickets.postman_collection.json`. Базовый URL коллекции — `http://localhost:5000`. Перед полным прогоном перезапустите backend, затем запускайте запросы по порядку: первый проверяет пустой список, POST сохраняют полученные ID в переменные `ticketId` и `cancelTicketId`. Коллекция содержит проверки кодов 200/201/400/404/409, отдельных PATCH, ограничений исполнителя и отмены.
