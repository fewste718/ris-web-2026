## Запуск клиента

Требуется Node.js 24 LTS версии 24.12 или новее.

```bash
cd frontend
npm install
cp .env.example .env
npm run dev
```

Открыть адрес из терминала, обычно http://localhost:5173.

В приложении три экрана: список заявок, создание заявки и вход. Запустите backend, откройте `/login` и войдите одной из учебных учёток ниже. Обычный режим использует настоящий API и PostgreSQL. Диспетчер видит общий реестр и создание; инженер — свои назначенные заявки.

В `.env` задаётся `VITE_API_BASE_URL=http://localhost:5000`. Этот файл исключён из Git, в репозитории хранится `.env.example`. После изменения переменной нужно перезапустить Vite. Для локального клиента API разрешает CORS с `http://localhost:5173`.

Для проверки в режиме разработки:

| Адрес | Проверка |
|-------|----------|
| `/login` | Вход, ошибка неверного логина или пароля |
| `/` | Список реальных заявок, доступных вошедшему сотруднику |
| `/new` | Создание диспетчером через API |
| `/?api=mock&mock=empty` | Учебная проверка пустого списка в dev |
| `/?api=mock&mock=500` | Учебная проверка ошибки списка в dev |
| `/new?api=mock&mock=500` | Учебная проверка ошибки создания в dev |

Mock включается только явным `api=mock` в режиме разработки и служит для воспроизведения состояний из ЛР6. Для проверки ЛР11 используйте обычные адреса без параметров. `/dev/api-check.html` остаётся отдельной учебной проверкой mock; в production-сборку она не входит.

Проверка сборки из папки `frontend`:

```bash
npm run build
```

## Запуск backend

Требуется .NET SDK 9.0. Проект использует `net9.0`.

Перед первым запуском выполните [настройку подключения и миграций](#подключение-api-к-postgresql).

Из корня репозитория:

```bash
cd backend
dotnet restore
dotnet run
```

Профиль `http` из `backend/Properties/launchSettings.json` задаёт среду `Development` и порт `5000`.

| Адрес | Назначение |
|-------|------------|
| `http://localhost:5000` | Базовый адрес API |
| `http://localhost:5000/swagger/index.html` | Интерактивный Swagger в Development; `/swagger` перенаправляет сюда |
| `http://localhost:5000/health` | Проверка живости процесса: HTTP 200 и `ok` |
| `http://localhost:5000/info` | Название приложения, среда, версия и номер лабораторной |

`/health` проверяет только живость процесса, а не создание заявки. Он не принимает поля заявки и не подтверждает работу POST. Создание и чтение заявок проверяются отдельными запросами API ЛР8.

API читает и сохраняет заявки в PostgreSQL через EF Core. После перезапуска API заявки, их номера, назначения и статусы сохраняются. На новой базе миграции создают справочники и учебные учётки. Vue использует этот API для входа, списка и создания.

`InfoController` получает `IApplicationInfoService` через конструктор; реализация зарегистрирована в DI в `Program.cs`. Сборочные папки `backend/bin` и `backend/obj` исключены из Git. Для остановки сервера нажмите Ctrl+C.

## API заявок

Главная сущность — `SupportTicket`, ресурс — `/api/support-tickets`. В теле создания передаются только `title`, числовой `equipmentId`, `description`. После удаления пробелов по краям длина темы — 5–80 символов, описания — 10–500. Сервер задаёт `id`, отдельный номер вида `SUP-2026-0001`, `New`, автора и время создания; исполнителя при создании нет. Организация-клиент определяется через оборудование.

| Метод и путь | Успех |
|--------------|-------|
| `POST /api/support-tickets` | 201, созданная заявка и Location |
| `GET /api/support-tickets` | 200, список или `[]` |
| `GET /api/support-tickets/{id}` | 200, одна заявка |
| `PATCH /api/support-tickets/{id}/assignee` | 200, исполнитель изменён, статус сохранён |
| `PATCH /api/support-tickets/{id}/status` | 200, статус изменён отдельным действием |

Для списка доступен фильтр `?status=New` или другой из четырёх статусов. Инженер получает только назначенные ему заявки, фильтр не расширяет этот список.

Каждый запрос к `/api/support-tickets` должен содержать `Authorization: Bearer <accessToken>`, полученный при входе. Сервер определяет действующего сотрудника и автора заявки по проверенному токену. `X-User-Id` не участвует в определении пользователя. Служебные `/health` и `/info` доступны без входа.

| ID сотрудника | Сотрудник | Действия |
|-----------|-----------|----------|
| 1 | Диспетчер 1 | Создать, назначить инженера при New, отменить New или InProgress |
| 2 | Инженер 1 | Читать свои заявки, переводить свою New в InProgress, затем в Closed |
| 3 | Инженер 2 | Те же действия только со своими заявками |

Оборудование: `7` — «Сетевой принтер 01», клиент `3` («Клиент А»); `8` — «Файловый сервер 01», клиент `4` («Клиент Б»). Допустимые исполнители — сотрудники `2` и `3`.

Назначение принимает `{ "assigneeUserId": 2 }`, смена статуса — `{ "status": "InProgress" }`. Назначение не переводит заявку в работу. Без исполнителя взять в работу нельзя. После начала работы переназначение запрещено, Closed и Cancelled неизменяемы. Отмена сохраняет запись и назначенного исполнителя. DELETE и общий PATCH отсутствуют.

Некорректный JSON, поля, справочные ссылки и неизвестные статусы возвращают 400; отсутствие действительного входа — 401; недостаточно прав или чужая заявка — 403; отсутствующая заявка — 404; недопустимое состояние при разрешённом действии — 409. Неожиданный сбой возвращает безопасный ProblemDetails с кодом 500; сервер пишет операцию, ID и тип ошибки без полного тела запроса.

В Postman выберите Import и откройте `docs/api-collection/support-tickets.postman_collection.json`. Базовый URL — `http://localhost:5000`. Запустите всю коллекцию по порядку: она выполняет вход учебных пользователей, создаёт собственные заявки и проверяет успехи и отказы. Прогон допускается на заполненной учебной БД; повторный запуск не требует её очистки. Созданные учебные заявки сохраняются.

## Вход и права

Выбран один способ: учебный JWT в заголовке `Authorization`. `POST /api/auth/login` принимает `login` и `password`, возвращает `accessToken`, `expiresAt` и `user` с полями `id`, `login`, `fullName`, `role`. `GET /api/auth/me` возвращает текущего пользователя по действительному токену. Неверный логин или пароль дают одинаковый ответ 401.

| Логин | Учебный пароль | Роль |
|---|---|---|
| `dispatcher1` | `Lab11-Dispatcher!2026` | Диспетчер |
| `engineer1` | `Lab11-Engineer1!2026` | Инженер 1 |
| `engineer2` | `Lab11-Engineer2!2026` | Инженер 2 |

Эти данные предназначены только для учебного контура. В таблице `users` хранятся хеши ASP.NET Identity PasswordHasher с солью, а не исходные пароли. Миграция `DemoUserPasswords` обновляет хеши существующих трёх учебных сотрудников, сохраняя их ID и заявки.

Токен действует 30 минут и хранится клиентом в `sessionStorage` текущей вкладки. Обновление страницы сохраняет вход, выход очищает сеанс и список. При 401 клиент предлагает войти снова. Это учебный способ хранения токена; пользовательские поля выводятся обычной интерполяцией Vue. Описание `<script>alert(1)</script>` должно быть видно текстом.

В Swagger выполните `POST /api/auth/login`, скопируйте `accessToken` и в **Authorize** вставьте токен без префикса `Bearer`. Затем выполняйте запросы к заявкам. Для проверки гостя очистите авторизацию.

Воспроизводимые HTTP-проверки из корня репозитория при работающем API:

```powershell
node scripts/verify-lab11.mjs
npm exec --yes --package=newman -- newman run docs/api-collection/support-tickets.postman_collection.json
```

Матрица разрешений и примеры кодов: [docs/role-matrix.md](docs/role-matrix.md). Результаты и снимки: [отчёт ЛР11](docs/reports/lab-11.md).

Из папки `frontend` команда `npm test` проверяет гонки сеанса и экранирование описания. При запущенном API `npm run test:integration` проверяет настоящие модули Vue с реальными HTTP-запросами и создаёт одну учебную заявку; браузер этот скрипт не запускает.

## PostgreSQL и SQL

Проверено на PostgreSQL 18.4. Таблицы `clients`, `equipment`, `users`, `support_tickets` соответствуют модели ЛР2. В SQL используются имена `snake_case`: например, `equipment_id` соответствует `equipmentId` в JSON. Клиент определяется через оборудование и не дублируется в заявке.

Команды этого раздела относятся к SQL-практике ЛР9 в базе `mobius_support_lab09`. База API подготавливается миграциями по инструкции в следующем разделе.

### Запуск SQL-скриптов

Откройте PowerShell из корня репозитория. Сервер PostgreSQL должен быть запущен. Укажите его порт и своего пользователя PostgreSQL; это учётная запись БД, а не диспетчер из таблицы `users`.

```powershell
# Добавляет инструменты только в PATH текущего терминала; поправьте версию при необходимости.
$env:PATH = "C:\Program Files\PostgreSQL\18\bin;$env:PATH"
$env:PGCLIENTENCODING = 'UTF8'
$env:PGOPTIONS = '-c timezone=UTC'
$dbHost = '127.0.0.1'
$dbPort = 5432
$dbUser = 'postgres'

# Создание базы выполняется один раз. Не используйте служебную БД postgres.
createdb -h $dbHost -p $dbPort -U $dbUser -W mobius_support_lab09
psql -X -h $dbHost -p $dbPort -U $dbUser -d mobius_support_lab09 -W -v ON_ERROR_STOP=1 -f db/schema.sql
psql -X -h $dbHost -p $dbPort -U $dbUser -d mobius_support_lab09 -W -v ON_ERROR_STOP=1 -f db/seed.sql
psql -X -h $dbHost -p $dbPort -U $dbUser -d mobius_support_lab09 -W -v ON_ERROR_STOP=1 -P pager=off -f db/queries.sql
```

Пароль PostgreSQL вводите по запросу; в файлы проекта его не записывайте.

**Повторная подготовка:** `schema.sql` удаляет четыре таблицы проекта вместе с данными и создаёт их заново. Выполняйте его только в отдельной учебной БД, затем снова запускайте `seed.sql`. Для обычного просмотра данных достаточно `queries.sql`.

В pgAdmin создайте отдельную учебную БД, откройте её Query Tool и по очереди выполните три SQL-файла. После подготовки в базе должны быть 2 клиента, 2 единицы оборудования, 3 сотрудника и 6 заявок: New — 2, InProgress — 2, Closed — 1, Cancelled — 1. В `queries.sql` находятся четыре SELECT: фильтр, сортировка, JOIN с названиями и GROUP BY с COUNT.

Для проверки сохранности остановите и снова запустите PostgreSQL, затем повторите SELECT. Схему и seed при этой проверке повторно выполнять не нужно.

## Подключение API к PostgreSQL

Требуются .NET SDK 9.0 и запущенный PostgreSQL. Версии зависимостей зафиксированы: EF Core и `dotnet-ef` 9.0.22, Npgsql 9.0.4. Локальный инструмент восстанавливается из `.config/dotnet-tools.json`.

Создайте в pgAdmin пустую учебную базу `mobius_support`. Подготовьте её через EF, начиная из корня репозитория:

```powershell
dotnet tool restore
dotnet restore backend/backend.csproj
cd backend

# Укажите свой адрес PostgreSQL, порт, пользователя и пароль.
dotnet user-secrets set "ConnectionStrings:Default" "Host=localhost;Port=5432;Database=mobius_support;Username=postgres;Password=ВАШ_ПАРОЛЬ"

# Один раз создайте отдельный случайный ключ подписи учебного JWT.
$randomBytes = New-Object byte[] 64
$rng = [Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($randomBytes)
$rng.Dispose()
@{ 'Jwt:SigningKey' = [Convert]::ToBase64String($randomBytes) } | ConvertTo-Json | dotnet user-secrets set

dotnet ef database update -- --environment Development
dotnet run --launch-profile http
```

Строка подключения и ключ JWT хранятся в `user-secrets` вне репозитория. Альтернатива — переменные окружения `ConnectionStrings__Default` и `Jwt__SigningKey`. В публичных конфигурациях значения этих секретов пустые. Повторно генерировать ключ перед каждым запуском не нужно: его замена прекращает действие ранее выданных токенов.

Миграция `InitialCreate` создаёт четыре таблицы с ограничениями и индексами, последовательность номеров заявок и начальные справочники: 2 клиента, 2 единицы оборудования, диспетчера и двух инженеров. Таблица заявок первоначально пуста. Повторный `database update` проверяет историю миграций и не пересоздаёт данные.

Для базы API не выполняйте `db/schema.sql` и `db/seed.sql`: это скрипты отдельной работы ЛР9. При изменении модели создавайте новую миграцию и применяйте её через `database update`. Созданные миграции и снимок модели сохраняются в Git.

Номер вида `SUP-2026-0001` формируется по году UTC и отдельной последовательности PostgreSQL. Она не сбрасывается при перезапуске API и выдаёт разные значения параллельным запросам. Пропуски после неудачных операций допустимы. Конфликт уникального номера возвращает 409.

### Проверка сохранности

1. Создайте заявку через Swagger или Postman и запишите `id`, `number`, `title`.
2. Назначьте инженера и выполните разрешённую смену статуса.
3. Остановите API через Ctrl+C, затем снова выполните `dotnet run --launch-profile http`.
4. Получите заявку по тому же ID. Номер, тема, исполнитель и статус должны совпасть.
5. В pgAdmin проверьте ту же базу и запись:

```sql
SELECT id, number, title, status, assignee_user_id
FROM support_tickets
WHERE id = 5; -- замените на полученный ID
```
